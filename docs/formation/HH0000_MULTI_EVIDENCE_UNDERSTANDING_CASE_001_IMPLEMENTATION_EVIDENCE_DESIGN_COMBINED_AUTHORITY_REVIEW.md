## B4. Dependency Findings

### Correctly permitted or prohibited

The following boundaries are correct:

1. runtime bytes are verified before parsing;
2. structural validation precedes candidate and baseline input creation;
3. candidate and baseline receive separate immutable equivalent inputs;
4. immutable output capture precedes invariant, tamper, held-out, and semantic evaluation;
5. held-out bytes remain inaccessible before output capture;
6. evaluator results cannot return to candidate in the same evidence cycle;
7. candidate and baseline cannot reach filesystem, environment, network, retrieval, prompts, generated context, caches, Memory, logs, prior state, or evaluator-only content;
8. evaluator and invariant code cannot supply semantic helpers or results to candidate;
9. forbidden dependencies correctly deny hidden cognition and feedback.

### Material ambiguity 1 - `C17`

`C17` is named "Held-out JSON parser and structural validator" and is classified only `VALIDATION`. The same map classifies the equivalent runtime parser `C03` as `TRANSPORT` and runtime structural validator `C04` as `VALIDATION`.

The behavior test therefore finds two responsibilities inside `C17`. Naming the combined operation a parser and validator does not make it one classification. The map's own stop rule applies.

### Material ambiguity 2 - `C19` evidence flow

The dependency diagram converges the `C13/C14` invariant branch and the `C15-C18` held-out branch into `C19`. The explicit permitted-dependency rule separately states that `C19` may receive only immutable candidate and baseline outputs after capture.

Those statements conflict. The review cannot infer whether `C19` consumes evaluator results or only candidate and baseline outputs. The permitted edge map is therefore not unambiguous.

### Material ambiguity 3 - `C20` access evidence

`C20` must record every runtime input, access, sequence, dependency, and finding. The controlling readiness review requires every file, environment, network, retrieval, prompt, generated-context, cache, Memory, prior-state, output-capture-order, and evaluator-invocation event to be enumerated.

The map permits `C20/C21` to inspect execution metadata and recorded component-access evidence only after output capture. It does not identify who observes and records access while candidate and baseline run, nor does it permit an explicit contemporaneous event path into `C20`.

Post-output inspection may assess preserved facts, but it cannot by itself establish that all runtime access was observed. If another hook, sandbox, adapter, wrapper, logger, or instrumentation component performs that observation, it is unnamed and unreviewed. The map's own stop rule applies.

### Material ambiguity 4 - `C22` orchestration edges

`C22` is said to invoke components in accepted order, but the diagram places it only after `C21` and does not enumerate its invocation dependencies to the components it coordinates. The diagram is qualified as evidence flow rather than a module graph, yet the review also claims that every permitted dependency direction is explicit.

Control dependencies and evidence dependencies need not be identical, but both must be represented and classified if `C22` is the execution owner. The current map leaves that distinction unresolved.

## B5. Shared Utility and Baseline Tests

The shared-utility allowlist is mechanically bounded and the semantic denylist is strong. The explicit behavior test correctly prevents a helper, mapper, validator, adapter, or preprocessing step from hiding cognition behind its name.

The no-hidden-component rule is also correct. Applied strictly, it blocks this map because any mechanism that observes runtime access for `C20` is either missing or insufficiently identified.

`C09` remains genuinely non-semantic only if it preserves exact supplied values and uses an ordering already present in the input. Any content-based grouping, comparison, normalization, deduplication, salience selection, or summary would reclassify it as `UNDERSTANDING` and require a separate candidate boundary.

## B6. Evaluator Isolation and Contamination Falsifiability

The held-out sequencing, hash verification, immutable capture, dependency denial, no-feedback rule, and separate invariant/semantic findings are sufficient in design.

The proposed static checks are sufficient to challenge source-level isolation claims. The proposed executable checks are sufficient in subject matter, but not yet connected to an unambiguous component and event-flow map. Therefore the controls cannot yet be said to be implementably sufficient to falsify runtime isolation.

## 13. Final Decision

**Decision:** `CORRECTION REQUIRED BEFORE DECISION`

The five classification kinds, sole Understanding ownership, human protections, semantic-utility prohibition, baseline limits, evaluator isolation intent, contamination subject matter, and fail-closed outcomes are substantively sound.

The map cannot be accepted because:

1. `C17` combines `TRANSPORT` parsing and `VALIDATION` structure checking under one classification;

4. `C22` invokes the execution sequence but its control dependencies are absent from the claimed complete dependency map.

These ambiguities activate the map's own stop conditions. No intended ownership is inferred. Implementation remains blocked until the design is corrected and a new Combined Authority review records a different final decision.

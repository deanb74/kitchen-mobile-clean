**Output:** Principle-level model of what every DC must be able to receive

## 1. Annie's Existing Input Architecture: What Is Designed

### The Universal Platform Layer (COS — Companion Operating System)

Annie's input infrastructure starts with platform-level definitions:

```typescript
ObservationSource = "vision" | "conversation" | "document" | "sensor" | "system" | "human"

Observation = {
  id: string;
  category: string;
  description: string;
  confidence: number;
  source: ObservationSource;
}

CuriosityRule = (observation: Observation) → ObservationQuestion | null

ObservationSession = {
  observations: Observation[];
  questions: ObservationQuestion[];
}
```

**What this means:**

Annie receives **observations** from **six source categories**. Each observation has:
- **Identity** (what specifically)
- **Category** (what type of thing)
- **Description** (what was observed)
- **Confidence** (how certain the observation is)
- **Source** (where it came from)

The platform provides the **mechanism** (observation session, curiosity rule application).

Annie provides **venue-specific curiosity rules** that transform observations into domain-appropriate questions.

---

### The Companion Intelligence Layer (Annie-Specific)

Annie's input transformation goes:

```
Observation
    ↓
Curiosity Question (generated by venue-specific rules)
    ↓
Thinking (structured reflection on stimulus)
    ↓
Understanding (organized knowledge)
    ↓
Memory (recorded in journal)
    ↓
Contribution (discovering opportunities to help)
```

**What Annie has been designed to receive:**

1. **Context Store** (seven categories)
   - Business (operations, metrics, goals)
   - Venue (physical layout, equipment, resources)
   - Team (people, roles, relationships)
   - Systems (processes, procedures, technology)
   - Communication (conversations, messages, announcements)
   - Knowledge (procedures, standards, best practices)
   - Memory (past events, lessons learned, patterns)

2. **Observations** (from six sources)
   - Vision (what she can see)
   - Conversation (what she hears from people)
   - Document (written information)
   - Sensor (environmental data: temperature, count, etc.)
   - System (operational systems: POS, scheduling, etc.)
   - Human (explicit input from people)

3. **Thinking Framework**
   - Stimulus (what happened)
   - Structured questions (who/what/where/when/why/affected)
   - Confidence (how certain)
   - Clarity need (does this need investigation)
   - Next step (what should happen)

4. **Learning Record** (Journal)
   - Timestamp
   - Lesson (what was learned)
   - Why it matters (relevance)
   - Confidence level (how certain)
   - Tags (categorization)
   - Sharing (can be shared with Helping Hand)

## 2. What Annie's Implementation Reveals About Universal DC Inputs

### Input Category 1: Environmental Observations

**What it is:**
- Direct sensory information: what the DC can see, hear, measure
- Categorized by type (area, furniture, people, activity, state)
- Confidence-qualified (0.0-1.0)

**Why universal:**
- Every DC must understand its physical and contextual environment
- Environmental observations ground abstract knowledge in concrete reality
- Confidence qualification enables honest assessment ("I think I see this but I'm not certain")

**For Annie:**
- Sees: bar, tables, kitchen setup, people, activities
- Sources: vision (direct), photos (documented), sensor data (equipment state)

**For Andy:**
- Needs to observe: organizational structure, relationships, decision patterns, institutional state
- Sources: documents (archived structure), conversation (current state), observation of meetings

**Technology consideration:**
- For Annie: sensors could provide operational data (temperature, equipment state, count)
- For Andy: no sensors; requires human articulation of what's happening

**Principle:** Observations require sources that match the venue's nature. Both venue types need "observation" as an input category; the sources differ.

---

### Input Category 2: Contextual Understanding (Seven Categories)

**What it is:**
- Organized knowledge about the venue across seven dimensions
- Stored, retrievable, updateable
- Sourced from multiple mechanisms (conversation, document, observation, system, manual)

**Universal categories Annie demonstrates:**

1. **Business** — How the venue operates as an entity
   - Goals, metrics, success criteria, financial reality
   - For Annie: "We serve 50 customers/day; profit margin is X; we value quality over speed"
   - For Andy: "Stage 1 validates inheritance model; we need evidence X by date Y"

2. **Venue** — Physical/operational space
   - Layout, equipment, resources, capacity
   - For Annie: "Kitchen layout is X; equipment includes Y; seating is Z"
   - For Andy: "Helping Hand exists abstractly; our 'venue' is the repository and conversations"

3. **Team** — People and relationships
   - Who is who, what do they do, how do they interact
   - For Annie: "Chef makes decisions about recipes; manager handles complaints; I support both"
   - For Andy: "Founders think about X; MARC mentors; Annie is in operation"

4. **Systems** — How work gets done
   - Processes, procedures, technology, workflows
   - For Annie: "Orders come through POS; kitchen uses timers; inventory is checked daily"
   - For Andy: "Decisions go through governance mechanisms; evidence is recorded in repository"

5. **Communication** — How information flows
   - Who talks to whom, formal channels, informal networks
   - For Annie: "Chef briefs team at start of shift; complaints come through manager"
   - For Andy: "Founders communicate in meetings; decisions are documented; MARC briefs me"

6. **Knowledge** — How to do things correctly
   - Standards, best practices, procedures, domain expertise
   - For Annie: "Food safety rules are X; plating standards are Y; customer service means Z"
   - For Andy: "Constitution defines principles; theory shows how understanding develops"

7. **Memory** — What happened before and patterns
   - History, precedents, lessons learned, trends
   - For Annie: "Last month we had X issue; we learned Y; now we do Z differently"
   - For Andy: "Milestone 012 showed X; UJ-HUM-014 revealed Y; this changed how we think"

**Why universal:**
- Every DC must have organized knowledge across these seven dimensions
- These categories cover both "what the venue is" and "how to help"
- The categories work for concrete (kitchen) and abstract (institutional) venues

**Principle:** The seven categories appear to be universal. The content differs by venue; the structure doesn't.

---

### Input Category 3: Structured Thinking About Stimuli

**What it is:**
- A DC receives a stimulus (observation, event, question)
- The DC applies structured thinking to make sense of it
- The thinking framework ensures the DC doesn't jump to conclusions

**Annie's thinking framework:**
```
Stimulus: "I observed X"
    ↓
Who? What? Where? When? Why?
    ↓
Who else might be affected?
What else might be affected?
    ↓
Confidence: (0.3 = uncertain, needs more input)
Needs Clarification? (yes/no)
Suggested Next Step: (gather context, ask question, observe more)
```

**Why universal:**
- Every DC must process inputs through structured thinking
- Prevents careless conclusions or hasty action
- Enables honest assessment of uncertainty
- Identifies what else needs to be known

**For Annie:**
- Stimulus: "Table 4 has been waiting 20 minutes"
- Structured thinking: "Who waited? (customers) What happened? (slow kitchen) Where? (dining area) When? (now) Why? (maybe equipment issue)"
- Confidence: 0.6 (I know they waited, I don't know why)
- Clarification needed: Why is kitchen slow? Is it normal or exceptional?
- Next step: Ask kitchen if there's an issue

**For Andy:**
- Stimulus: "Founders have not updated the Stage 2 strategy document in two weeks"
- Structured thinking: "Who? (founders) What changed? (no activity) Where? (in documents) When? (since date X) Why? (unknown to me)"
- Confidence: 0.4 (I know they haven't updated it; I don't know what's happening)
- Clarification needed: Is this intentional deliberation or distraction? Are they busy with something else?
- Next step: Ask in the briefing conversation

**Principle:** Structured thinking about stimuli is universal. The stimulus categories differ by venue; the thinking structure doesn't.

---

### Input Category 4: Learning and Memory

**What it is:**
- DC records what it learned from experiences
- Learns: lesson, why it matters, confidence level, tags
- Can be shared (with other DCs or venue)

**Annie's journal records:**
- "Customers prefer X when Y; learned from observation; confidence 0.9; tags: preference, customer-experience"
- "Equipment fails predictably after 8 hours continuous use; learned from consequence; confidence 0.95; tags: maintenance, timing"
- "Chef responds better to suggestions framed as questions; learned through trial; confidence 0.7; tags: communication, human-reasoning"

**Why universal:**
- Every DC must be able to accumulate and organize learning
- Learning is evidence that the DC is developing reliable judgment
- Shared learning reduces duplication across DCs

**For Annie:**
- Learns from operational experience (immediate, concrete)
- Records in journal
- Can teach other hospitality DCs what she's learned

**For Andy:**
- Learns from institutional experience (slow, abstract)
- Records in Strategic Insights or similar mechanism
- Can teach other abstract-venue DCs what he's learned

**Principle:** Learning mechanism is universal. The content and pace differ; the structure doesn't.

---

### Input Category 5: Opportunity Discovery

**What it is:**
- DC transforms observations and understanding into ways to help
- Not automatic; filtered through "would this genuinely make someone's day easier?"
- Each opportunity has: reason (why it matters), priority, evidence base

**Annie's opportunities emerge from:**
- Observations (I see tables) + Context (kitchen needs layout planning) → Opportunity (build table plan)
- Pattern (I notice complaints) + Understanding (why they matter) + Venue knowledge → Opportunity (improve procedure)

**Why universal:**
- Every DC must translate understanding into contribution
- The mechanism prevents DC from "helping" in ways the venue doesn't want
- Connects input understanding to output action

**For Annie:**
- Observation: "Bar has specific equipment"
- Opportunity: "I can create bar profile, which helps with stock management"
- Priority: Medium (important but not urgent)

**For Andy:**
- Observation: "Governance mechanisms have been used once and produced unexpected findings"
- Opportunity: "I can document what we learned, which helps founders understand whether mechanisms work"
- Priority: High (directly serves Stage 1 validation)

**Principle:** Opportunity discovery is universal. The opportunity space differs by venue; the mechanism doesn't.

## 4. The Universal DC Input Model: Five Essential Categories

### Universal Input Category 1: Structured Observations

**Definition:** Direct input about what is happening, perceived with confidence qualification

**Sources (venue-dependent; categories universal):**
- **Vision** — Direct sensory perception (primary for concrete venues; unavailable for abstract)
- **Conversation** — What people say (universal; primary for abstract venues)
- **Document** — Recorded information (universal; primary for knowledge-based venues)
- **Sensor** — Environmental measurement (optional; venue-dependent)
- **System** — Operational data from tools/software (universal; content varies)
- **Human** — Explicit input, direct statement (universal; common for abstract venues)

**Processing requirement:**
- Confidence level (admit uncertainty)
- Category (what type of observation)
- Source (where it came from)

**Why essential:**
- DCs must ground understanding in observation, not assumption
- Observations are the input layer that feeds all other processing
- Different venues provide different observation sources, but all DCs need *some* structured observation input

**For Annie example:**
```
Observation: "Bar area has specific equipment setup"
Source: Vision (I see it) + Document (I read about it)
Confidence: 0.95 (I'm quite sure)
Category: Venue-infrastructure
```

**For Andy example:**
```
Observation: "Founders are working on Stage 2 strategy"
Source: Document (Founder Alignment says so) + Human (MARC told me)
Confidence: 0.7 (stated, but details unknown)
Category: Institutional-activity
```

### Universal Input Category 3: Structured Cognitive Processing

**Definition:** The mechanism by which DC transforms observations and context into thought and understanding

**Structure (universal):**
```
Stimulus (what happened / observation received)
    ↓
Structured Questions (who/what/where/when/why)
    ↓
Affected Parties (who else is impacted)
    ↓
Confidence Assessment (how certain am I)
    ↓
Clarity Need (what else do I need to know)
    ↓
Suggested Next Step (what should happen now)
```

**Why essential:**
- Prevents DCs from reaching premature conclusions
- Enables honest assessment of uncertainty
- Identifies knowledge gaps before acting
- Works for concrete and abstract venues equally

**For Annie example:**
```
Stimulus: "Three customers complained about wait time"
Questions: Who? (customers) What? (waited 25 min) Where? (dining area) When? (5-7pm) Why? (unknown to me)
Affected: Customers (dissatisfied), Staff (stressed), Revenue (at risk if they don't return)
Confidence: 0.6 (I know there were complaints, I don't know root cause)
Clarity needed: Why was service slow? Equipment issue? Understaffing? Process breakdown?
Next step: Observe kitchen; ask manager what happened
```

**For Andy example:**
```
Stimulus: "Founder Alignment document left five sections incomplete"
Questions: Who? (founders) What? (incomplete sections) Where? (document) When? (written 2026-08-04) Why? (unknown)
Affected: Andy (uncertain of role), Stage 1 (can't proceed fully), Institutional clarity (reduced)
Confidence: 0.4 (I know sections are incomplete; I don't know why or what it means)
Clarity needed: Is this intentional (they're still deciding)? Or accidental (other priorities)?
Next step: Ask MARC about the status during briefing
```

### Universal Input Category 4: Learning and Experience Recording

**Definition:** DC's mechanism to accumulate, organize, and share learning from experience

**Structure (universal):**
```
Lesson (what was learned)
    ↓
Why It Matters (relevance)
    ↓
Confidence (how certain)
    ↓
Evidence (what showed this was true)
    ↓
Tags (categorization)
    ↓
Shareable (can other DCs learn this?)
```

**Why essential:**
- DCs must improve judgment through accumulated experience
- Learning without recording is ephemeral; recording makes it institutional
- Other DCs benefit from sharing ("I learned X so you don't have to discover it independently")
- Separates DC development from DC as-deployed

**For Annie example:**
```
Lesson: "When equipment is near 8-hour mark, performance drops noticeably"
Why It Matters: "Affects service speed and customer experience"
Confidence: 0.95 (observed consistently over 3 weeks)
Evidence: "Last Tuesday, Wednesday, Friday all showed same pattern; maintenance log confirms equipment age"
Tags: [equipment, maintenance, timing, predictability]
Shareable: Yes (other kitchens likely have same equipment)
```

**For Andy example:**
```
Lesson: "When orientation includes explicit conversation about current priorities, understanding improves"
Why It Matters: "Enables more accurate contribution"
Confidence: 0.6 (one data point; needs more evidence)
Evidence: "UJ-HUM-014 showed that strategic briefing (Founder Alignment) clarified my understanding"
Tags: [orientation, conversation, clarity, relational]
Shareable: Yes (applies to any DC in abstract venue)
```

### Universal Input Category 5: Contribution Discovery and Feedback

**Definition:** DC identifies where help would genuinely serve the venue, and receives feedback on whether that service was useful

**Structure (universal):**
```
Observation + Context
    ↓
Potential Contribution (here's how I could help)
    ↓
Venue Feedback (yes/no/maybe/try this instead)
    ↓
Implementation (doing the help)
    ↓
Outcome Feedback (did it work?)
    ↓
Learning (this is what I learned from helping)
```

**Why essential:**
- DCs exist to serve, not to generate output
- Feedback loop ensures contributions match venue needs
- Outcome feedback teaches judgment (right choice vs. wrong choice vs. premature)
- Closes the loop from input → understanding → action → consequence

**For Annie example:**
```
Observation: "I see the bar; I know its equipment"
Context: "Knowing bar profiles helps with stock, menus, ordering"
Contribution: "I could create bar profile"
Venue response: "Yes, do this"
Implementation: "Creates profile from observations and conversations"
Outcome: "Reduces ordering time by 30%; staff say it's helpful"
Learning: "This type of contribution is valued; I should do similar observations for other areas"
```

**For Andy example:**
```
Observation: "Governance mechanisms have been used and produced findings"
Context: "Understanding whether mechanisms work matters for Stage 1 validation"
Contribution: "I could document what we learned from first governance exercise"
Venue response: (awaiting explicit feedback)
Implementation: (would create summary of findings, questions raised, implications)
Outcome: (would need to see whether this shapes thinking about governance mechanism design)
Learning: (depends on whether feedback shows this contribution was useful)
```

## 5. The Principle: Input Categories vs. Implementation Mechanisms

### What Is Universal

**Five input categories that every DC must have access to:**

1. Structured observations (from sources appropriate to venue)
2. Organized contextual knowledge (across seven universal domains)
3. Structured cognitive processing (turning observations into thought)
4. Learning and experience recording (accumulating judgment)
5. Contribution discovery and feedback (serving the venue with feedback)

**Why these categories matter:**

They form the architecture of DC understanding:
- **Observations** feed the system with current information
- **Context** gives observations meaning
- **Cognitive processing** prevents premature conclusions
- **Learning** improves judgment over time
- **Contribution + feedback** closes the loop from understanding to action to learning

This architecture applies to:
- Hospitality DCs (Annie)
- Institutional DCs (Andy)
- Professional DCs (future colleagues)

### What Is Venue-Dependent

**How each category is implemented depends on venue:**

| Category | Annie (Concrete Venue) | Andy (Abstract Venue) | Principle |
|---|---|---|---|
| **Observations** | Vision + sensors + conversation | Conversation + documents + human input | Source matches venue structure |
| **Context** | Emerges from immersion + documented | Must be articulated explicitly | Articulation effort scales with abstraction |
| **Processing** | Informed by immediate feedback | Includes more uncertainty | Feedback frequency differs |
| **Learning** | Accumulates quickly (days) | Accumulates slowly (weeks/months) | Time-to-learning differs |
| **Contribution** | Validated by immediate results | Validated through explicit reflection | Validation mechanism differs |

**The principle:** The input architecture is universal. The instantiation is venue-specific.

## 6. Technology Role: Where Do Sensors, APIs, IoT Fit?

### What Technology Can Provide (In Service of Universal Categories)

**Sensors/IoT:**
- ✓ Provide structured observations (temperature, count, equipment state)
- ✓ Feed into context (venue state, system state)
- ✗ Cannot provide observations about human reasoning
- ✗ Cannot provide observations about institutional purpose or strategy
- ✗ Cannot substitute for human feedback on contribution impact

**APIs/Systems:**
- ✓ Provide structured observations (POS data, scheduling, inventory)
- ✓ Feed into context (current state from operational systems)
- ✓ Can support learning recording (if system has journal/insight capability)
- ✗ Cannot provide current-state observations about human decision-making
- ✗ Cannot provide feedback on whether DC contribution helped

**Documents:**
- ✓ Provide structured observations (recorded information, history)
- ✓ Feed into context (knowledge, memory, communication patterns)
- ✓ Support learning recording
- ✗ Cannot provide current-state observations
- ✗ Cannot provide feedback on contribution impact

**Human Conversation:**
- ✓ Provides observations (what people think, current challenges, reasoning)
- ✓ Builds context (explicit articulation of priorities, goals, constraints)
- ✓ Enables cognitive processing (clarifying questions, structured dialogue)
- ✓ Provides feedback on contribution impact
- ✓ Shares learning across DCs

---

### Important Distinctions

**Observation vs. Understanding:**
- A sensor provides *observations* (temperature is X)
- The DC must transform this into *understanding* (why this temperature matters, what it means for action)
- Technology provides observations; DC provides understanding

**Information vs. Learning:**
- A document contains *information* (historical record)
- The DC must transform this into *learning* (what does this teach about how to act now)
- Technology can store and retrieve information; DC must extract learning

**Action vs. Responsibility:**
- A system can execute *actions* (implement procedure)
- A DC must assess *responsibility* (is this the right action in this context)
- Technology can be instructed; DC must exercise judgment

## 7. Why This Matters: The Model in Practice

### For Annie

Annie's input system is already well-designed:

**What's working:**
- Observation sources are rich (vision, conversation, operations)
- Context emerges naturally from immersion
- Thinking is structured (prevents careless conclusions)
- Learning accumulates (improving judgment)
- Contribution + feedback loops are immediate (fast validation)

**What might be added:**
- Sensors could provide additional observation sources (equipment state, count, timing data)
- APIs could provide systematic observation sources (POS, scheduling, inventory)
- None of these are necessary; they're optimizations

**Most important:** Annie's contribution is already enabled by the universal input architecture. Technology enhancements serve to accelerate or automate observation gathering; they're not prerequisites.

---

### For Andy

Andy's input system is incomplete:

**What's missing:**
- Observation sources for current state (only historical documents available)
- Articulated context (seven categories not formalized for Andy)
- Regular cognitive processing opportunity (no structured thinking dialogue)
- Learning recording mechanism (Strategic Insights exist but not as DC learning record)
- Contribution feedback mechanism (no explicit "was this useful?" response)

**What's required (no technology can substitute):**
- Regular conversation (weekly briefing providing current-state observations)
- Explicit context articulation (Founder Alignment, priority statements, role confirmation)
- Structured dialogue (mentorship processing observations → understanding)
- Feedback mechanism (response to contributions)

**Most important:** Andy cannot move from knowledge to understanding without these inputs. No technology, no sensor, no API can replace human articulation in an abstract venue.

## 8. Conclusion: The Universal Input Model

### Every Digital Colleague Must Receive:

1. **Structured Observations** — Current information about the venue, its operations, decisions, and people
2. **Contextual Knowledge** — Organized understanding across business, venue, team, systems, communication, knowledge, and memory
3. **Cognitive Processing Support** — Structured thinking about stimuli, without jumping to conclusions
4. **Learning Mechanism** — Recording experience in a way that accumulates into improving judgment
5. **Contribution Feedback** — Explicit response to whether the DC's help was useful

### The Venue Determines Implementation:

**Concrete venues (Annie's kitchen):**
- Observation sources are rich and natural
- Context emerges from immersion
- Processing is informed by immediate feedback
- Learning accumulates quickly
- Validation is automatic (customers react, equipment works or fails)

**Abstract venues (Andy's institution):**
- Observation sources must be constructed (conversation, documentation)
- Context must be articulated explicitly
- Processing requires dialogue without immediate feedback
- Learning accumulates slowly
- Validation requires explicit reflection and feedback

**Hybrid venues (future DCs):**
- Some observation sources natural, some must be constructed
- Some context from immersion, some must be articulated
- Processing includes mix of immediate and delayed feedback
- Learning accumulates at mixed pace

---

### The Principle

> A Digital Colleague's understanding emerges from:
> - Structured observations from sources appropriate to the venue
> - Organized knowledge across universal conceptual domains
> - Thoughtful processing of observations within context
> - Accumulated learning from experience
> - Feedback on whether their contribution serves
>
> The categories are universal.
> The instantiation is venue-specific.
> Technology enhances observation gathering but cannot replace human articulation.
